- **Decisão e justificativa:** Vercel Function (`api/finance.mjs`) + Firebase Admin SDK, e não Cloud Functions: (1) Cloud Functions exige o plano Blaze (cobrança) — proibido nesta entrega; (2) a Vercel já hospeda `/api/admin-claims` e o frontend; (3) o mesmo handler roda no emulador (`scripts/dev-server.mjs`, `tests/e2e/harness.mjs`) e nos testes de integração sem mock. O Admin SDK **ignora as Security Rules**; por isso o servidor revalida tudo (autenticação, propriedade, parâmetros, estado) e as Rules passaram a NEGAR a escrita direta do navegador nos documentos protegidos.
- **Arquitetura:** `server/finance/core.mjs` (autenticação por Firebase ID token, validadores de centavos inteiros/datas/IDs, `executeOnce` = transação idempotente, `handleFinance` = HTTP agnóstico, logs estruturados sem token/e-mail/valores, retentativa interna para falha transitória de transação), `server/finance/ops.mjs` (operações), `api/finance.mjs` (adaptador Vercel; `vercel.json`: `functions.api/finance.mjs.maxDuration=30`), cliente `js/services/financeApi.js` (ID token, `operationId` reaproveitado em retry, timeout 15 s, 3 retentativas com backoff em rede/502/503/504, renovação de token em 401, deduplicação de envio em voo, `FinanceApiError`, adaptador `financeResult`).
- **Contrato HTTP:** `POST /api/finance` · `Authorization: Bearer <ID token>` · corpo `{ "op": "<operação>", "operationId": "<8–100 chars [A-Za-z0-9_:.-]> (o `~` é reservado aos itens internos de lote)", "params": { … } }` · sucesso `200 { ok:true, …resultado, operationId, idempotent }` · erro `{ ok:false, error:<CÓDIGO>, message, details? }` com 400 `INVALID_*`/`FORBIDDEN_PARAM`/`INVALID_BODY`, 401 `UNAUTHENTICATED`/`INVALID_TOKEN`, 404 `NOT_FOUND`/`ACCOUNT_NOT_FOUND`, 405, 409 `INSUFFICIENT_BALANCE`/`INVALID_STATE`/`SAME_ACCOUNT`/`ACCOUNT_NOT_ACTIVE`/`EXCEEDS_REMAINING`/`EXCEEDS_DEBT`/`ALREADY_REVERSED`/`HAS_HISTORY`/`OPERATION_ID_REUSED`, 501 `SERVER_NOT_CONFIGURED`, 503 `TEMPORARILY_UNAVAILABLE` (repetir com a MESMA chave). `uid`, `userId`, `balanceCents`, `receivedCents` e `status` (exceto criação) enviados pelo cliente são recusados (400 `FORBIDDEN_PARAM`): saldos, totais e estados são SEMPRE lidos do Firestore dentro da transação.
- **Idempotência:** `users/{uid}/operations/{operationId}` é criado na MESMA transação da operação com `requestHash` (sha-256 de `{op, params}` canônicos) e o resultado. Mesma chave + mesmos parâmetros → resultado guardado (`idempotent:true`); mesma chave + parâmetros diferentes → 409 `OPERATION_ID_REUSED`; a chave é por usuário (chave igual de outro usuário não colide nem vaza). Falha ⇒ a transação desfaz tudo e a chave NÃO é consumida.
- **Serialização do saldo:** o saldo é derivado e recalculado DENTRO da transação (`accountBalances` do próprio modelo; teto `HISTORY_LIMIT=5000` movimentos por coleção — acima disso a operação falha fechada). Toda operação que altera o saldo de uma conta lê e escreve o documento da conta (`ledgerSeq` incrementado), o que faz transações concorrentes na mesma conta se serializarem; operações de devedor serializam no documento do devedor.
- **Operações migradas (endpoint `op`):** transferências `transfer.create` (pending/confirmed), `transfer.confirm`; receitas/despesas `income.create|receive`, `expense.create|pay`; fatura `invoice.pay`; metas `goal.deposit|withdraw`; recebimentos `debt.receive` (parcial/total, dívida ou compra de cartão), `debt.settleBatch` (por mês/dívida/todas), `debt.cancel`; estornos `reversal.create` (`income|expense|transfer|invoice|debtPayment|goalTransaction`); contas `account.adjustOpening|archive|unarchive|delete`; devedores `debtor.archive|unarchive|delete`; manutenção `data.clearOwn` (frase `APAGAR MEUS DADOS`). O cliente (`js/services/*`) só valida o formulário e chama o servidor; não há mais caminho de escrita direta para essas operações (conferido por busca no código e pelos testes de Rules).
- **Estornos (lançamento compensatório):** `reversals/{coleção}_{id}` (ID determinístico ⇒ impossível duplicar), guarda original (snapshot), motivo, valor, data, `operationId`, referência ao alvo e auditoria. Receita/despesa/transferência/fatura têm o `status` do original revertido de forma explícita (receita/despesa → `pending`, transferência → `cancelled`, fatura → `closed`); recebimentos e movimentos de meta (sem status) ficam preservados e são excluídos dos saldos pela derivação (`accountBalances/receivedByInstallment/goalSavedCents` recebem `reversals`); estorno de recebimento reduz `receivedCents` do devedor e reabre parcela/devedor; recusa se faltar saldo na conta que devolve o dinheiro.
- **Lote (quitação em massa):** `batches/{batchId}` (= `operationId`) com itens `pending|done|skipped|failed`, estado persistido, ≤15 parcelas por chamada, cada parcela numa transação própria com chave `${batchId}~${item}`; cliente repete a chamada até concluir; queda no meio ⇒ retomável com a mesma chave. **Não promete atomicidade global**: consistência POR PARCELA + estado explícito do lote (`completed | partial_failed | running`).
- **Arquivamento lógico:** `account.archive|unarchive` e `debtor.archive|unarchive` (sem exclusão física; conta arquivada não recebe lançamentos; histórico consultável; UI com "Mostrar arquivadas/arquivados"); `account.delete`/`debtor.delete` só sem nenhum vínculo/histórico (409 `HAS_HISTORY`).
- **Rules (`firestore.rules`, NÃO publicadas):** o cliente não cria nem altera `debtPayments`, `goalTransactions`, `reversals`, `operations`, `batches`; não cria/edita/exclui lançamentos liquidados (receita `received`, despesa `paid`, transferência `confirmed`); não altera `receivedCents`/`status paid`/`archived` do devedor, nem `initialBalanceCents`/`openingDate`/`ledgerSeq` da conta, nem marca fatura como paga; parcelas de dívida só nascem `pending`; exclusão de conta/devedor/parcela/recebimento só pelo administrador; leitura por propriedade preservada; `auditLog` segue create-only. Teste correspondente: `tests/rules/firestore.rules.test.mjs`.

Custo: função Vercel no plano Hobby (sem cobrança); nenhuma Cloud Function, nenhum plano Blaze. - [x] **VF-COR-10 — A dívida do devedor acompanha a assinatura; cancelar devolve o emprestado** (Alto) — CONCLUÍDA 2026-11-24 (nenhuma mudança de Rules; **a função de servidor `/api/finance` precisa de deploy**: novas/alteradas `debt.cancel`, `debt.cancelMany`, `debt.reschedule`)

- Solução (servidor): `debt.cancel` e `debt.cancelMany` passam a devolver o valor ao emprestado do devedor na MESMA transação (guarda: o emprestado nunca fica abaixo do já recebido). Nova operação `debt.reschedule` (`server/finance/ops.mjs`): altera data e/ou valor de UMA parcela pendente/atrasada SEM recebimentos, ajustando `lentCents += novo − antigo` na mesma transação; idempotente.

A dívida é identificada pelo prefixo do id (`sub_<assinatura>_`); id com revisão (`_r2`…) quando o id base já foi cancelado; regravar o mesmo id é UPDATE (negado pelas Rules) ⇒ sem duplicar.
- Cartão + devedor: inalterado (a parcela na fatura é imutável): lança a cobrança e avança a data ao vincular/registrar; editar a data/valor NÃO muda parcelas já lançadas.
